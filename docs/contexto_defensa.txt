------------------------------------------------------------
0. QUE ES EL PROYECTO
------------------------------------------------------------

Es un clon simplificado de Airbnb hecho con DOS aplicaciones
independientes que consumen la MISMA API REST (backend compartido por
todo el curso, Laravel):

- APP CLIENTE: carpeta app-cliente/, hecha en Flutter (Dart) +
  provider (estado) + dio (HTTP). Permite buscar lugares, ver el
  detalle y hacer una reserva. Corre en un emulador/celular Android.

- APP ARRENDATARIO: carpeta app-arrendatario/, hecha en Ionic +
  Angular standalone (TypeScript) + HttpClient + signal(). Permite
  publicar lugares (con fotos y ubicacion en un mapa) y ver las
  reservas que le hicieron. Se prueba en el navegador (ionic serve) Y,
  desde la Fase E2, tambien como app nativa Android empaquetada con
  Capacitor (npm run build && npx cap sync android && npx cap run
  android) - ver seccion 6.4.

El enunciado exige que cada app use una tecnologia distinta vista en
clase. Es un proyecto INDIVIDUAL: el docente evalua que el autor
entienda y pueda explicar cada linea, por eso todo el codigo usa
nombres en español y patrones simples (sin librerias de estado
"magicas" como Bloc/Riverpod/NgRx, sin generadores de codigo).

Las dos apps NO comparten ningun archivo de codigo.

Durante TODO el desarrollo (incluida la Fase E) las dos apps corren
contra un mock local (Mockoon), no contra la API real - ver seccion
2 (URL de cada app segun como corre) y seccion 7 (comandos).

2. CONTRATO DE LA API (lo esencial para poder defender)
------------------------------------------------------------

Backend Laravel compartido por todo el curso. Reglas clave (SIN
cambios en la Fase E: la fase es solo visual):

- TODOS los errores (validacion, no encontrado, credenciales malas)
  responden HTTP 404, salvo el login con contraseña incorrecta, que da
  HTTP 401. Para decidir que mensaje mostrar hay que mirar la FORMA
  del cuerpo de la respuesta, no el codigo HTTP:
    * {"message": "texto"}              -> error de negocio, se
                                            muestra tal cual
    * {"campo": ["mensaje", ...], ...}   -> error de validacion, se
                                            toma el primer mensaje del
                                            primer campo

- Rutas usadas (metodo, ruta, quien la usa):
    POST cliente/registro            Cliente
    POST cliente/login               Cliente
    POST arrendatario/registro       Arrendatario
    POST arrendatario/login          Arrendatario
    POST lugares/search              Cliente (busqueda simple)
    POST lugares/advancedsearch      Cliente (busqueda avanzada)
    GET  lugares/{id}                Ambas
    GET  lugares/arrendatario/{id}   Arrendatario
    POST lugares                     Arrendatario (crear)
    PUT  lugares/{id}                Arrendatario (editar; NO es POST
                                      con id adentro, eso duplica)
    POST lugares/{id}/foto           Arrendatario (multipart, un
                                      archivo por peticion)
    GET  reservas/cliente/{id}       Cliente
    POST reservas                    Cliente (crear reserva)
    GET  reservas/lugar/{id}         Arrendatario

- latitud/longitud SIEMPRE como texto (string), nunca numero: la API
  rechaza numeros con error de validacion.

- precios (precioNoche, costoLimpieza, precioNoches, precioLimpieza,
  precioServicio, precioTotal) vuelven como TEXTO ("30.00") en casi
  todas las respuestas, pero como NUMERO en la respuesta inmediata de
  crear/editar un lugar. Los modelos tienen que tolerar ambos casos.

- fotos[].url viene apuntando a un dominio VIEJO y caido
  (bnb-backend.loca.lt). Hay que ignorar ese dominio: tomar solo el
  nombre de archivo (lo ultimo despues de la ultima /) y reconstruir
  la URL contra la base ACTUAL de la API (sin /api) + /fotos/archivo.

- Busqueda avanzada: ciudad es obligatoria y exacta; descripcion es
  parcial; cantPersonas/cantCamas/cantBanios/cantHabitaciones/
  tieneWifi/cantVehiculosParqueo/precioNoche son todos de coincidencia
  EXACTA (no minimo/maximo). Un campo que el usuario no llena se debe
  OMITIR del body, nunca mandarlo en 0 (mandar 0 filtra literalmente
  por "0").

- GET reservas/cliente/{id}: cada reserva trae el campo "lugar" como
  un ARREGLO DE 1 ELEMENTO (no un objeto), con el lugar completo
  (fotos, arrendatario) adentro.

- GET reservas/lugar/{id}: la respuesta ES el lugar completo, con un
  arreglo "reservas" adentro (cada reserva trae su "cliente" anidado).
  No es un arreglo plano de reservas.

URL de la API segun cada app y como corre (actualizado en la Fase E,
reemplaza cualquier URL anterior de este documento):
  - Cliente (app-cliente/lib/config/api_config.dart, linea 6): SIEMPRE
    http://10.0.2.2:3001/api (la app solo corre en el emulador
    Android, nunca en el navegador).
  - Arrendatario con `ionic serve` (navegador, misma PC):
    src/environments/environment.ts, linea 8 -> http://localhost:3001/api.
  - Arrendatario empaquetado con Capacitor (`npm run build`, lo que
    usa `npx cap sync android`/`npx cap run android`):
    src/environments/environment.prod.ts, linea 6 -> http://10.0.2.2:3001/api
    (10.0.2.2 es el alias fijo con el que el emulador de Android llega
    a la PC que lo hospeda; "localhost" dentro del emulador apuntaria
    al propio emulador, no a la PC con Mockoon).
  Las tres URLs apuntan al mock local de Mockoon durante todo el
  desarrollo (ver seccion 7); la API real se activa en los 3 archivos
  recien antes de la defensa.

RG-02 - Ambas apps exigen iniciar sesion antes de entrar
------------------------------------------------------------
ARCHIVOS:
  Arrendatario: app-arrendatario/src/app/guards/auth.guard.ts
    lineas 8-18 (la funcion authGuard completa)
  Arrendatario: app-arrendatario/src/app/app.routes.ts
    lineas 18, 24, 29, 35 (canActivate: [authGuard] en cada ruta
    protegida)
  Cliente: app-cliente/lib/main.dart lineas 18-19 (cargarSesion) y 48
    (home: ... haySesion ...)

SNIPPET (auth.guard.ts, lineas 8-18):
  export const authGuard: CanActivateFn = () => {
    const authService = inject(AuthService);
    const router = inject(Router);

    if (authService.haySesion()) {
      return true;
    }

    router.navigate(['login']);
    return false;
  };

SNIPPET (main.dart, lineas 18-19 y 48):
  final authProvider = AuthProvider();
  await authProvider.cargarSesion();
  ...
  home: authProvider.haySesion ? const BusquedaScreen() : const LoginScreen(),

FLUJO (arrendatario):
  1. Angular intenta activar una ruta protegida (ej. mis-lugares).
  2. Antes de activarla, corre authGuard (declarado en app.routes.ts).
  3. authGuard llama a authService.haySesion(), que lee localStorage.
  4. Si hay sesion guardada, deja pasar (return true). Si no, navega a
     /login y bloquea la ruta (return false).

FLUJO (cliente):
  1. main() (lineas 14-22 de main.dart) espera authProvider.
     cargarSesion() ANTES de llamar a runApp.
  2. Segun authProvider.haySesion (true si hay un usuario cargado),
     MaterialApp.home es BusquedaScreen o LoginScreen directamente -
     no hay "redireccion", se elige la pantalla inicial una sola vez.

PREGUNTAS:
  "¿Que pasa si borro la sesion guardada a mano?" -> En el proximo
  intento de entrar a una pantalla protegida (arrendatario) o en el
  proximo arranque de la app (cliente), se manda al login.
  "¿Por que el guard es una funcion y no una clase?" -> Es el estilo
  CanActivateFn de Angular standalone (mas moderno y corto que la
  interfaz CanActivate de una clase @Injectable).

  const double porcentajeServicio = 0.10;

  int calcularNoches(DateTime llegada, DateTime salida) {
    return salida.difference(llegada).inDays;
  }

  double calcularSubtotal(int noches, double precioNoche) {
    return _redondear(noches * precioNoche);
  }

  double calcularServicio(double subtotal) {
    return _redondear(subtotal * porcentajeServicio);
  }

  double calcularTotal(double subtotal, double limpieza, double servicio) {
    return _redondear(subtotal + limpieza + servicio);
  }

  double _redondear(double valor) {
    return double.parse(valor.toStringAsFixed(2));
  }

6.4 CAPACITOR Y ANDROID (ARRENDATARIO, DESDE LA FASE E2)
------------------------------------------------------------
Ademas de `ionic serve` (navegador), la app arrendatario corre como
app NATIVA Android empaquetada con Capacitor: `npm run build && npx
cap sync android && npx cap run android`.

ARCHIVO: app-arrendatario/capacitor.config.ts (completo, 16 lineas):
  const config: CapacitorConfig = {
    appId: 'bo.edu.nur.bnb_arrendatario',
    appName: 'bnb Anfitriones',
    webDir: 'www',
    // En desarrollo la app llama a Mockoon por http://10.0.2.2:3001: con el
    // esquema https por defecto Android bloquea esas peticiones (no son HTTPS).
    server: {
      androidScheme: 'http',
      cleartext: true,
    },
  };

Por que androidScheme/cleartext: desde Android 9, el sistema bloquea
por defecto cualquier peticion HTTP que no sea HTTPS. En desarrollo la
app llama a Mockoon por http://10.0.2.2:3001 (HTTP simple);
androidScheme: 'http' hace que la propia app se sirva a si misma por
HTTP (en vez de HTTPS, su valor por defecto) y cleartext: true
autoriza explicitamente ese trafico sin cifrar. Deja de ser necesario
(pero no molesta) cuando se use la API real por HTTPS.

ARCHIVOS: app-arrendatario/src/environments/environment.ts (19
  lineas) y environment.prod.ts (8 lineas) - cual URL usa la app segun
  como corre:

6.6 FUNCION PLURALIZAR (LAS DOS APPS)
------------------------------------------------------------
Agregada en el ajuste posterior a la Fase E2 para corregir cantidades
que se mostraban siempre en plural (ej. "1 baños"). Misma idea en las
dos apps: antepone la cantidad y elige singular o plural segun si es 1.

CLIENTE: app-cliente/lib/utils/conversiones.dart, lineas 46-49:
  // Antepone la cantidad y elige singular o plural, ej. "1 baño" o "2 baños".
  String pluralizar(int cantidad, String singular, String plural) {
    return '$cantidad ${cantidad == 1 ? singular : plural}';
  }
Usado en: widget/caracteristicas_lugar.dart (personas, camas, banios,
  habitaciones, vehiculos de parqueo), widget/lugar_card.dart
  (huespedes), widget/reserva_card.dart (noches), screen/
  confirmar_reserva_screen.dart (noches, huespedes).

ARRENDATARIO: app-arrendatario/src/app/utils/formato.ts, lineas 35-38:
  // Antepone la cantidad y elige singular o plural, ej. "1 baño" o "2 baños".
  export function pluralizar(cantidad: number, singular: string, plural: string): string {
    return `${cantidad} ${cantidad === 1 ? singular : plural}`;
  }
Usado en: pages/mis-lugares/mis-lugares.page.ts (expuesta al template
  en la linea 72) + mis-lugares.page.html (camas, banios), pages/
  reservas-lugar/reservas-lugar.page.ts (linea 69) + reservas-lugar.
  page.html (noches).

PREGUNTA: "¿Por que recibe el singular y el plural como texto en vez
  de agregar una 's' automaticamente?" -> En español el plural no
  siempre es "agregar s" (habitación -> habitaciones); es una funcion
  generica reutilizable para cualquier palabra, no una regla
  gramatical completa.

7. COMO SE EJECUTA EL PROYECTO (comandos, por si el docente pide
correrla; incluye Mockoon y ambas formas de correr el arrendatario)
============================================================

MOCK LOCAL (Mockoon, se usa durante TODO el desarrollo, incluida la
Fase E - la API real se activa recien antes de la defensa):
  npx @mockoon/cli start --data contexto/mockoon-backend-airbnb.json --port 3001
  Mismas rutas, formas y casos de error que docs/API.md, con casos
  simulados por valores magicos (password:"incorrecta",
  email:"noexiste@example.com", id:99999, ciudad:"sin-resultados").

APP CLIENTE (Flutter, SIEMPRE en emulador/celular Android):
  cd app-cliente
  flutter run -d <id-del-emulador-o-celular>
  (requiere el emulador Android ya prendido y Mockoon corriendo;
  api_config.dart ya apunta a http://10.0.2.2:3001/api)

APP ARRENDATARIO - opcion 1, navegador (mas rapido para iterar):
  cd app-arrendatario
  ionic serve
  (abre http://localhost:8100; usa environment.ts, que ya apunta a
  http://localhost:3001/api; en Chrome, F12 -> Ctrl+Shift+M para vista
  movil)

APP ARRENDATARIO - opcion 2, emulador Android con Capacitor (para
probar como se ve/corre la app nativa, Fase E2):
  cd app-arrendatario
  npm run build
  npx cap sync android
  npx cap run android
  (usa environment.prod.ts, que ya apunta a http://10.0.2.2:3001/api;
  requiere el emulador Android ya prendido)

Antes de la defensa, cuando el docente confirme que la API real
responde: cambiar las 3 URLs (api_config.dart, environment.ts,
environment.prod.ts) a la URL real. Con Mockoon NO se puede probar el
flujo cruzado entre apps (el mock siempre devuelve el mismo lugar fijo
"Casa Azul", sin importar lo que se cree o edite); recien con la API
real se puede probar asi, en orden:
  1. Arrendatario: crear un lugar nuevo con nombre distintivo, foto
     real y ubicacion en el mapa; guardar.
  2. Cliente: buscar esa misma ciudad y confirmar que aparece ese
     lugar nuevo con los datos correctos (foto, nombre, descripcion,
     huespedes, precio).
  3. Abrir su detalle y verificar que los 8 datos de RC-12 coinciden
     con lo que se lleno en el formulario del arrendatario.
  4. Reservarlo desde el cliente (elegir fechas) y confirmar; revisar
     "Mis reservas" del cliente.
  5. Arrendatario: abrir "Ver reservas" de ese mismo lugar y confirmar
     que la reserva aparece con el cliente, fechas, noches y total
     correctos (noches x precio + limpieza + 10% de servicio).
  6. Editar el precio del lugar en el arrendatario y confirmar que el
     cliente ve el precio actualizado al volver a abrir el detalle.
